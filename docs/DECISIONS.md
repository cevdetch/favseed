# Decisions

Every decision is backed by a measurement. The originals were taken over a 39-mark corpus that
does not ship with this repository; the ones marked **re-measured** have been reproduced
against `test/fixtures/`, and where the two disagree the reproducible number wins.
`docs/BENCHMARKS.md` is generated by `node bench/bench.mjs --write` and is the current truth;
the reports under `bench/` hold the measurements each sweep there regenerates.

## The accuracy bar

`pct <= 1.0 %`: the share of pixels whose colour distance from the reference exceeds 8/255,
measured on **both** a white and a black composite so that alpha error cannot hide in either.
Distance is the largest single-channel difference: an error passes only when it is invisible in
every channel, not when it is small on average.

Reference = an unquantised resvg render of the **var-resolved source** at the same size, not
of favseed's own `icon.svg`, which would make the gate blind to the geometry error the SVG
stage introduces before a rasteriser is ever involved.

RMSE is reported alongside but does not gate: error is driven by *size*, not by the mark, so
one RMSE threshold is the wrong shape. At 16 px almost every pixel is an anti-aliasing edge.

**The bar is a statement about the sizes favseed ships by default**: 180, 192 and 512, the
padded PNGs. It is not reachable at every size a user can ask for, and pretending otherwise
would make it meaningless: a small icon is almost all edges, and no palette reproduces an
anti-aliasing ramp to 8/255. The 48 px ICO payload is scored the same way and reported
separately: across 20 fixtures its worst source error is 1.215 %, on two small-grid marks
([bench/ico-size](../bench/ico-size/README.md)). If you ask for `--sizes 16`, you get the best
16 px icon this pipeline can make, and it is not within 8/255 of a reference render. Nothing is.

The same metric gates the SVG stage itself, at 512 px on the static appearance (decision 5).
That budget is a separate check: it says nothing about the PNGs at other sizes or qualities.

Three readings of "colour distance" were compared (largest channel, Euclidean/√3, mean
channel) and they agree to within 0.06 pp at the default sizes. The metric's shape does not
matter here: pixels that differ, differ by a lot, because palette snapping is a jump rather
than a drift.

## Priority

**Smaller output beats faster build.** The bytes ship to every visitor forever; the build
happens once. A change that costs bytes to save build time needs explicit approval and
measured tradeoffs. The current default is one such trade, taken on those terms: it skips
Zopfli, and `--zopfli` opts back in (decision 8).

The accuracy bar is a *constraint*, not one side of that trade. Where bytes and the bar
conflict, the bar wins, and decision 24 turns on that.

## Decisions in force

### 1. svgo is a dependency, imported, with the plugins as plain objects

`svgo` runs in process; the custom plugins are objects in `lib/core.mjs`. Importing removed a
`mkdtemp` config directory, ~110 lines of `String.raw` plugin source no linter or editor can
see into, and an env-var channel (`FAVICON_VARS`/`MODE`/`REPORT`). **It does not make the CLI
faster, and the original claim that it would was wrong:** `import 'svgo'` cost **309 ms** (a
`-V` that imported it took 355 ms against a 46 ms bare-node baseline), while the two svgo CLI
spawns it replaced ran *in parallel* for ~180 ms. The in-process passes themselves were 5 ms and
14 ms, so the work was never the cost: the module graph is. That is why `bin/favseed.mjs` loads
svgo on the first `optimiseSvg` call and not at import: `--help`, `-V` and option validation
never pay for it. **Re-measured:** output was byte-identical across 70 outputs on 7 fixtures × 2
modes when the spawns were replaced. A *global install* of svgo is not importable by bare
specifier (`ERR_MODULE_NOT_FOUND`; `NODE_PATH` does not work for ESM); as a package dependency
it is.

### 2. `var()` is resolved by a custom plugin, before `inlineStyles` and `minifyStyles`

`resolveVars` sits ahead of `preset-default` in both passes, behind only the document-level
comment strip, the animation strip (so a `var()` used only by motion cannot fail a
`--no-animation` build that drops it) and the keyframes hoist of decision 18. Byte-identical
to a separate pre-pass, with one fewer parse. Handles nested fallbacks and values containing
`/ & , ( )`, spaces and quotes; **fails with a clear error** on an unresolvable property,
naming `--var` and, in the default pass, `--no-animation`.

### 3. resvg never sees `var()`

resvg 0.48.1, the version inside `@napi-rs/image` 1.15.0 (decision 26), has no `var()`
support: it warns and renders the whole mark **black**. Every raster is rendered from the
selected, var-resolved `icon.svg` (decision 5), never from the source.

### 4. One `icon.svg`, animation and accessibility preserved by default

The set carries one SVG, used for the favicon `<link>` and on pages alike. The default pass
keeps motion, styling and accessibility: `role` survives (`removeUnknownsAndDefaults`
`keepRoleAttr`), `cleanupIds` preserves every id an ARIA IDREF names, and `pruneRefs` replaces
svgo's blanket class and id removal, keeping exactly the classes a selector names and the ids
something references. SMIL can name an id in `begin="x.end"`, which no pattern would catch, so
id pruning is skipped entirely when SMIL is present.

`--no-animation` (`animation: false`) is the static pass: the structural animation strip (SMIL
elements, `@keyframes`, any `@media` on `prefers-reduced-motion`, and `animation*` /
`transition*` declarations wherever they are), then `preset-default` +
`convertStyleToAttrs` + `removeAttrs{(role|aria-.*|data-.*|class)}` + `removeDimensions` +
`removeTitle` + `removeDesc{removeAny}`, `multipass`. `preset-default` alone leaves
`aria-label` and turns the stylesheet into `style="fill:…"`; `convertStyleToAttrs` fixes the
second, `removeAttrs` the first. `removeAny` because svgo's default keeps any non-empty
`<desc>`, and `general.svg`'s 87-byte description was 30 % of its 289-byte static SVG. svgo
4's `preset-default` has no `removeViewBox`, and the dependency range starts at 4.1.0, so
there is nothing to override.

Rasters render the base appearance in both modes: resvg does not sample an animation timeline.
Measured when the second SVG was removed (decision 12): complete-set bytes fall 2.0 % across
four fixtures ([bench/zopfli/DEFAULTS.md](../bench/zopfli/DEFAULTS.md)).

### 5. SVG precision is selected per mark, against the 1 % bar at 512 px

Full builds try `floatPrecision` 1, 2, 3, 4, 6 and 8 in turn, each from the original source,
and keep the first whose static 512 px render meets the bar on both composites against a
minimally prepared reference (`lib/svg-precision.mjs`). A candidate that makes a whole mark
disappear fails even under 1 %. If none passes, `icon.svg` keeps the source's numeric geometry
and the build warns.

1 is the first candidate because it is the smallest precision inside the bar on the mark built
to test it. **Re-measured** on `heavy.svg` at 256 px, svgo error only: `floatPrecision 0` →
828 B, pct **1.7319 %, fails**; `1` → 1539 B, 0.4074 %; `3` → 3875 B, 0.0000 %. A single fixed
precision was wrong for marks drawn at other scales, which is why it became a search. From
[bench/precision](../bench/precision/README.md):

- Generated 1-, 16- and 24-unit marks had SVG errors of 15.622 %, 1.882 % and 1.544 % at
  precision 1; the search picks 3, 2 and 2 and lands them at 0.699 %, 0.451 % and 0.583 %. A
  .001-unit mark that failed to build now builds at precision 6.
- `gradient.svg` no longer has its stops rounded from `.42/.78` to `.4/.8`: its SVG-stage error
  falls from 2.478 % to 0 %.
- On the original 11 fixtures the default set costs **963 more PNG/ICO bytes (1.4 %)** and two
  more SVG bytes; `heavy` and the nine other non-gradient marks keep precision 1 and identical
  files. Worst final PNG source error falls from 2.097 % to 0.114 %.

The budget grades the static base appearance only: not animation frames, media states or other
display sizes.

### 7. Keep whichever of the quantised and lossless encodes is smaller

`engine.encode` builds both from the same raw render, `pngQuantize` and `losslessCompressPng`,
and keeps the smaller; a tie keeps the quantised one (`lib/engine.mjs`). The guard is not inert:
the last native benchmark, over 50 files at 256 colours, had the undithered quantisation winning
42, a Floyd-Steinberg one 1 and the lossless path 7, and keeping the smallest of those three
candidates saved 0.29 % against always taking the undithered one (`docs/BENCHMARKS.md` as of
2026-10-04). Without it, raising `--colors` produces *larger* files and nothing reports it:
measured on `gradient.svg` in that pipeline, the lossless path won at 16 px from 128 colours and
at 16 and 32 px at 256, because pngquant's palette overhead exceeded what oxipng's own colour
reduction achieved on a small image.

The guard has a limit, and it is stated rather than papered over: quality is not monotonic in
size even with it in place. On the production path, quality 99 and 95 produced 75 838 and
74 610 PNG bytes against 73 938 at 100 ([bench/zopfli/QUALITY.md](../bench/zopfli/QUALITY.md)).
The guard does not add a second encode to force monotonicity; it only refuses the larger of the
two it already has.

The hardcoded ICO `wBitCount = 32` (decision 9) is proved right for a truecolour payload by a
unit test with a synthetic RGBA payload, compared with `icotool -c -r` wherever icotool is
installed. The gradient fixture can no longer prove it, because its ICO payload is now indexed
at quality 80 and 100.

### 8. Zopfli is opt-in, and runs once, on the winner of that comparison

`--zopfli` (`zopfli: true`) re-deflates the encode's winner with Zopfli: 120 iterations in
`mode: 'release'`, 15 in `mode: 'fast'` (`lib/config.mjs`). Without it, both modes produce the
same bytes. Finishing only the winner is what decision 7's comparison buys: Zopfli-ing both
paths tripled the cost for zero extra bytes in the native pipeline. Apart from the
palette pass below, the finish keeps the encode's row filters and every other chunk, and it is
dropped when it is not smaller. The order is
the one decision 6 measured: the quantiser re-encodes from scratch, so nothing that recompresses
can run before it.

**Off by default, because the trade is lopsided.** Measured over tiles, general, heavy and
gradient ([bench/zopfli/DEFAULTS.md](../bench/zopfli/DEFAULTS.md)): the old default (120
iterations) took 59.610 s and wrote 39 266 PNG/ICO bytes; the Zopfli-off default that replaced
it, then still at quality 100, took 0.903 s and wrote 40 449, **66.0× faster for 1 183 B
(3.0 %)**, with every decoded pixel unchanged. Under
the priority rule that is a byte cost for build time, so it is stated here and kept one flag
away.

**120 iterations when it runs.** From `docs/BENCHMARKS.md`, the finish over the 192 and 512 px
encodes of ten marks:

| iterations | bytes | vs 15 | seconds |
|---|---|---|---|
| 15 | 57 159 | 0 | 27.8 |
| 120 | 57 066 | −0.16 % | 133.2 |
| 240 | 57 046 | −0.20 % | 254.7 |

240 doubles the time again for a further 0.04 pp, so the knee stays at 120 for a release build;
15 is the fast mode's count. Size is not monotonic per file: four of 44 PNGs were smallest at a
lower count, but picking each file's best would have saved 9 B in total
([bench/zopfli/EFFORT.md](../bench/zopfli/EFFORT.md)).

**One guarded palette pass.** Before deflating a bare PNG with a full 256-entry palette, the
finish tries one lossless `Sub`-filter re-encode and keeps it only if smaller. Across 44 PNGs it
changed two gradient outputs, 10 669 → 10 560 B at 120 iterations, with identical decoded pixels
on all 88 comparisons ([bench/zopfli/COMPETITOR.md](../bench/zopfli/COMPETITOR.md)).

### 9. `favicon.ico`: one 48×48 entry, raw PNG payload, container written in JS

**48, not 32.** Across 20 fixtures the 48 px payload adds 1 946 B (about 97 B a mark, 1.5 % of
the complete set), and the worst ICO source error falls from 1.660 % to 1.215 %; the marks over
1 % fall from four to two ([bench/ico-size](../bench/ico-size/README.md)). Every other file is
byte-identical between the two. An explicit `--sizes 32` still writes a 32 px PNG.

**A PNG payload, not BMP.** The BMP payload icotool writes by default was **8.8× larger** over
the fixtures (39 340 B against 4 479 B), and favseed's 22-byte writer was **byte-identical to
`icotool -c -r` on 10/10** (`docs/BENCHMARKS.md` as of 2026-10-04; the suite still asserts the
identity wherever icotool is installed). Writing it in JS removed the only dependency with no
npm package and no Windows build.

`wBitCount` is the field to get wrong: the directory entry describes the *decoded* 32-bit
image, not the encoding, so it is 32 even for a 4-bit paletted payload, and `bColorCount` is 0
for one too. `icoWrap` reads the payload's IHDR and refuses to write a header that disagrees
with it (decision 17).

### 10. `--bg` defaults to opaque black, warned about, validated by the renderer

iOS composites transparent Home Screen icons onto **black**, so black is what the platform
would have produced from a transparent icon anyway. The default matches that instead of
substituting white without a word, and the file is smaller for it (no tRNS, simpler palette).
A mark drawn on a light ground wants `--bg '#fff'`, which is why the warning fires whenever
the flag is absent.

The value is validated by rendering one pixel with it through the engine (`engine.probe`)
rather than by a colour table, so `rgb()`, `rgba()` and `hsl()` all work and the validator can
never disagree with the renderer. A name list rejects `rgb()`, and a loose `/^[A-Za-z]+$/`
accepts `nonered`. Parsing proves nothing about opacity, so the probed pixel must also come out
opaque: `transparent`, `rgba(…, 0.5)` and `#ffffff80` all parse, and would put alpha into icons
declared maskable. They are refused with a pointer to `--bg none`. Applies to every padded icon
(`apple-touch-icon.png` and each `icon-<size>.png`, decision 22); the ICO payload stays
transparent. Corners stay square; the OS applies its own mask.

### 11. `--sizes` defaults to `192 512`

*(Reversed. The original was `256 512`.)* The documentation every browser is held to asks for
both: web.dev's install criteria ("must include a 192px and a 512px icon", 2024-09-19),
Chrome's Lighthouse installable-manifest doc (2024-04-16) and MDN's Making PWAs installable
(2026-09-07). Desktop Chromium's code is looser: `installable_evaluator.cc` accepts one `any`
icon of 144 px or more, and Chromium 152's `Page.getInstallabilityErrors` reported no error for
a manifest with only a 512. That is one engine on one platform, with Android, Edge, Samsung
Internet and Firefox untested, so the documented pair wins; the 192 costs 159 B on a flat mark.
SVG cannot stand in for either: an SVG entry makes the Android WebAPK install fail
([crbug.com/40925759](https://issues.chromium.org/issues/40925759)).

### 14. One render per distinct (SVG, size, background)

Jobs are keyed on the placed SVG, the size and the ground (`lib/pipeline.mjs`). `--sizes 48`
therefore renders twice on purpose: once padded on `--bg` for `icon-48.png`, once unpadded and
transparent for the ICO payload, for different bytes. Under `--bg none` the icon is unpadded
too, so the two share one job and "the ICO payload is `icon-48.png`" holds by construction.
`--sizes 180` shares the apple icon's job the same way.

### 17. resvg does not stretch; it fits

`resvg -w 32 -h 32` on a 128×64 mark produces a **32×16** PNG. The aspect ratio wins and the
second dimension is derived, so with no warning the non-square path was emitting non-square
"32 px icons" and an ICO whose 32×32 header disagreed with its own payload.

The first fix forced a square: `width`/`height` put back and `preserveAspectRatio="none"`. That
made the rasters square by **stretching** the mark, which the accuracy reference, stretched the
same way, could not see. The rasters now nest the original rectangular viewport, centred, in a
square canvas (`squareIconSvg` in `lib/core.mjs`). Nothing is rewritten, so percentage lengths
and shifted origins keep their coordinate plane, and `icon.svg` keeps its own viewport: the
wrapper exists only for rasterisation. Against literal square goldens, the `wide` fixture's worst
PNG source error fell from 8.312 % to 0 % and its raster bytes from 2 333 to 1 754 (−24.8 %);
the ten square fixtures are byte-identical ([bench/framing](../bench/framing/README.md)). A
viewBox more than 1 % from square warns on stderr.

`icoWrap` reads the payload's IHDR and refuses to write a header that disagrees with it. That
is what turned a wrong file that passed without complaint into a failed build.

### 18. Two svgo 4.1.0 bugs sit on the animated-input contract itself

Both are triggered by `@keyframes` inside `@media (prefers-reduced-motion: no-preference)`,
which is the shape the animated-input contract (README, "Animation") recommends. Both bite the
default pass, the one that keeps the stylesheet.

**The crash.** `lib/style.js parseStylesheet` skips a top-level `@keyframes`, because its
percentage selectors are not selectors. For any *other* at-rule it runs an inner
`csstree.walk` that collects every descendant `Rule` with no such guard, so `0%` and `100%`
land in the rule table svgo matches elements against. Everything that resolves a computed
style then feeds them to css-select:

```
Error: Unmatched selector: %   at css-what parse.js:128
  ... css-select is() -> svgo lib/xast.js matches() -> lib/style.js computeOwnStyle()
```

That path is reached from `removeDeprecatedAttrs`, `removeUnknownsAndDefaults`,
`inlineStyles` and more, so disabling one plugin only moves the crash. favseed **hoists** any
`@keyframes` nested in an at-rule out to the top level of the same stylesheet instead, which
removes the input that triggers it. The hoist is safe: `@keyframes` has no cascade and no
conditional behaviour, it only defines a name. What decides whether the mark moves is the
`animation` declaration, and that stays inside the guard. `--no-animation` has already deleted
every `@keyframes`, so only the default pass hoists.

**The silent one, which is worse.** `inlineStyles` copies a rule's declarations onto the
elements it matches and then deletes the `class` attribute it consumed, without checking
whether a rule it *left alone* still selects that class. It leaves two kinds alone: rules
inside an at-rule (its `useMqs` default of `['', 'screen']` is compared against a string
built as `` `media screen` ``, so in practice nothing inside an at-rule qualifies) and rules
with a pseudo-class. Motion lives in both. `minifyStyles` then hands csso a usage list built
from the classes still in the document, csso drops the `@media` rule as unused, and the
animation disappears from `icon.svg` with no warning at all.

**The hazard is per name, not per file**, and getting that wrong costs bytes. A name is only
at risk when *both* are true: some rule svgo will not inline selects it, **and** some rule it
will inline selects it too. The common shape (palette classes at the top level, a motion
class named only inside the guard) is safe, because nothing inlines the motion class and so
nothing strips it. The first version of this check asked the coarser question ("is any class
selected inside an at-rule?"), switched inlining off for those marks as well, and added 44 B
to a real seven-block logo whose output had been byte-stable until then.

Three fixes were measured on the animated fixture, through the full plugin list:

| fix | bytes | result |
|---|---|---|
| `inlineStyles` off | **473 B** | guard kept, class kept |
| `inlineStyles removeMatchedSelectors` off | 534 B | guard kept, class kept |
| `minifyStyles usage.classes` off | 445 B | guard kept, **class gone, animation dead** |

The smallest *correct* option wins, and it is only reached when a class is at risk under the
per-name test above: a mark whose motion selects nothing by class still gets the full inlining.
`tiles.svg` and `animated.svg` pin the two directions.

### 20. Masked icons at their documented sizes, placed by measurement, snapped to whole pixels

The measurement below is the **default** of `--padding` (`auto`): an explicit percentage
overrides it (decision 22). What it measures, and the snap that follows it, are unchanged.

**Which files the platforms read:**

| Consumer | What it reads | Source |
|---|---|---|
| Chrome install criteria | `any` icons at 192 and 512 px (the code on desktop accepts one of 144 px or more) | web.dev, Chrome docs, MDN; `installable_evaluator.cc` |
| Chrome's launcher icon (Android, ChromeOS, macOS) | `maskable` first, falling back to `any`; Android's minimum is 83 px | `installable_icon_fetcher.cc` |
| Android WebAPK | PNG and JPEG are sent to the server; an SVG entry fails the install | `webapk_single_icon_hasher.cc`, crbug.com/40925759 |
| iOS and iPadOS | `apple-touch-icon` over manifest icons; 180, 167 and 152 px documented; `purpose` and SVG ignored | Apple's Configuring Web Applications, firt.dev's iOS PWA notes |
| Windows | `any` icons, drawn without a plate on light and dark | Microsoft Learn, app icon and PWA icon guidance |

**One padded set, at the documented sizes.** `apple-touch-icon.png` stays 180 px, the largest
size Apple documents. Every `--sizes` entry is padded into the safe zone the same way and the
set is declared `"any maskable"` (decision 22); there is no separate `icon-maskable-512.png`.
An earlier draft of this decision made a single 512 px `apple-touch-icon.png` serve both. No
source recommends a 512 px apple icon, so it was reverted: Apple's guide only says iOS would
scale a larger one.

**One file carries both purposes.** This reverses what this decision first said: that `"any"`
stays transparent and separate because web.dev advises against `"any maskable"` on one file.
The advice is real and the cost is real (decision 22 states it in full): on a platform that
does not mask, the padded icon shows a smaller mark on its ground. But two files cost a second
512 px render, a second manifest entry, and (the deciding point) a mark that can only ever be
in one of the two places: padded for the mask or full-bleed for the desktop. The set is padded
into the safe zone, so it is both in fact. Chrome also will not install a PWA whose icons are
all `maskable`; it needs at least one `any`. `--bg none` opts out of all of it: transparent,
unpadded, `"any"` only.

**Measured placement.** The farthest opaque pixel's outer corner, found on a render at the
icon's own size, decides the scale. On the C mark, iOS's 22.37 % rounded mask cut 12 of 14 310
mark pixels from the unplaced 180 px icon, and none after. A source opaque in all four corners
is full-bleed and used as it is.

**Snapped to whole pixels.** An exact fit put every edge of the C mark between pixels
(measured at the then-default `--colors 8`):

| Icon | Placement | Mark box | Colours | Edge pixels | Bytes |
|---|---|---|---|---|---|
| maskable 512 | exact fit | 330 px | 12 | 1 905 | 571 B |
| maskable 512 | snapped | 320 px | 3 | 0 | 290 B |
| apple 180 | snapped | 112 px (fit 116) | 3 | 0 | 151 B |

The snap walks the box down in whole even pixels (so the offset is whole too) and stops at
10 % below the fit. It takes the size with the fewest pixels under partial coverage, and only
when that at least halves them, so a curved mark, anti-aliased at every size, keeps its exact
fit and is never shrunk for nothing.

**Bounded probes.** The walk renders one probe per candidate box, in batches of four (one at a
time above a 512 px canvas or a 1024 px fitted box). A mark with a large transparent margin is
enlarged well past its canvas, and probing at that box size cost one small-mark diagnostic a
3 164 px render. When the fitted
box exceeds twice the canvas, each probe now renders that box centred on the target canvas
instead; both are even, so the offset stays whole and the selection is unchanged. Three
small-extent diagnostics went from 23.367 s to 2.453 s with identical files; the 20-fixture
corpus is unchanged at 4.698 → 4.709 s, callback for callback
([bench/placement](../bench/placement/README.md)).

### 21. An isomorphic core, because the website runs the same SVG stage

Everything that needs no filesystem, no child process and no Node built-in lives in `lib/`:
the svgo stage, the ICO, the mask maths and manifest (`core.mjs`), the options (`config.mjs`),
the precision search (`svg-precision.mjs`), the raster stage (`engine.mjs`), the whole build as
bytes (`pipeline.mjs`) and the Zopfli adapter (`zopfli.mjs`). Those modules import only each
other. `bin/favseed.mjs` keeps what only Node does: config loading, the native engine, staging
and the atomic publish, `build()` and `cli()`.

The alternative was reimplementing it in the browser, against a second set of bugs, with no
gate able to tell the two apart. Sharing the code is the lesser evil by a wide margin.

**Three seams make it work, and each is a parameter rather than a bundler trick:**

- **svgo is injected.** `createSvgStage({ optimize })` takes whichever svgo build the caller
  already has loaded: the synchronous `optimiseSvg` helper on the package root loads Node's
  `svgo` (`bin/favseed.mjs`:95-97), while `build()` loads the self-contained `svgo/browser`
  bundle instead, on both the CLI and the website (`bin/favseed.mjs`:181-183), to avoid pulling
  in svgo's Node dependency tree on a first build. Both export `optimize`, so the plugin list
  is one list. No aliasing, no conditional exports, nothing to misconfigure without an error.
- **The engine is injected.** `createEngine({ image, zopfli, inflate })` takes the native
  `@napi-rs/image` and `node:zlib` in Node, and its WASM build and `DecompressionStream` in the
  page. Both get the same `lib/zopfli.wasm`.
- **The mask maths takes decoded pixels**, from the engine's `renderRgba` in every host, and
  **`icoWrap` works in `Uint8Array` and `DataView`**, so no host carries another's decoder.

**Measured:** a first website version ran a different quantiser (`image-q`) and an oxipng
without Zopfli, and its PNGs came out 2.4–6.2 % larger than the CLI's on typical marks and
**117 %** larger on the gradient at `--colors 8`. On one engine the outputs are the same files:
matching self-contained input, options and mode produce identical bytes, links and placement
([site/README.md](../site/README.md)). The browser's single-thread compatibility build matched
native SHA-256 on 184 files across 31 fixture and option cases
([bench/browser-compat](../bench/browser-compat/README.md)).

**The split also broke the published package, for a short while.** `bin/favseed.mjs` imports
`../lib/core.mjs`, and `files` shipped only `bin` and `astro`, so the tarball would have
installed and then thrown `ERR_MODULE_NOT_FOUND` on first run. `lib` now ships and the
tarball test asserts it by name: the one assertion standing between the split and a broken
publish.

### 22. `--padding`: measured by default, fixed on request, one set for both purposes

Decision 20 measures where the mark goes. This decision is about who chooses the number, and
about collapsing the two-file set (`any` plus `maskable`) into one.

**No fixed percentage is correct for every mark.** The W3C safe zone is a *circle* of radius
40 % of the icon; how much of it a mark can use depends on its shape. A round mark fills 80 %
of the width; a square mark's corners touch the circle when the box is 56.6 % of the width,
needing 21.7 % padding per side. Measured across the fixtures, `auto` chooses:

| fixture | box / canvas | padding it chose |
|---|---|---|
| `gradient` | 434/512 | 7.6 % per side |
| `general` | 408/512 | 10.2 % |
| `heavy` | 366/512 | 14.3 % |
| `tiles` | 320/512 | **18.8 %** |

A fixed 11 % (the "20 px of 180" figure) is right for a round mark and pushes a square one's
corners outside the safe circle. So `auto` stays the default and an explicit `--padding`
percentage is the override: applied as given (`box = canvas * (1 - 2p)`, rounded down to an
even pixel so the offset stays whole) and never snapped, because snapping exists to find a
crisper size *near* the measured fit and moving a number the caller chose would make the flag
mean something different from what it says. Capped at 45: 50 leaves no mark at all, and a
value that produces an empty icon should be a message rather than a blank PNG.

**`"any maskable"` on one file.** Chrome will not install a PWA whose icons are all
`maskable` (it needs at least one `any`), so the padded set cannot be `maskable` alone, and
maintaining a second unpadded file doubles the 512 px cost for a mark that can only sit in one
place. The set is padded into the safe zone, so `"any maskable"` is honest.

**The cost, stated in full.** `icon-192.png` and `icon-512.png` are padded and opaque. On a
platform that does *not* mask (most desktops), they render as a smaller mark inside the `--bg`
ground rather than edge to edge. That is the trade web.dev warns about, and it is the default.

**`--bg none` opts out of all of it.** Transparent, unpadded, manifest purpose `"any"` only: the
spec lets a platform composite a transparent icon onto any colour, so the safe zone would mean
nothing, and padding the ICO fallback only makes the mark smaller. An explicit `--padding`
then reaches only `apple-touch-icon.png`, and the CLI says so after the build.

### 23. Released through trusted publishing, so `provenance` is not set by hand

The original package contract specified `"publishConfig": {"access": "public", "provenance": true}` and a
release workflow holding an `NPM_TOKEN`. Both changed before the first publish.

**No token.** `release.yml` publishes through npm trusted publishing: the job's OIDC token is
exchanged for a short-lived publish credential, so there is no long-lived secret to leak or
rotate, and the version is **staged** (`npm stage publish`) rather than published. Nothing is
live until the maintainer approves it with 2FA. On that path npm attaches provenance without
being asked; the flag adds nothing there.

**The flag would break the first publish.** npm only lets a package configure a trusted
publisher once the package exists, so 1.0.0 is published by hand (`RELEASING.md`). Provenance
can only be generated inside a supported CI, and with `provenance: true` in `publishConfig` a
publish from a laptop fails instead of proceeding. `publishConfig` is therefore
`{"access": "public"}`.

The job also installs with `--ignore-scripts`: it is the one job holding the OIDC token, so no
dependency lifecycle script runs in it. The only system package it installs is icoutils, so the
ICO equivalence test runs rather than skips.

### 24. `--colors` defaults to 256: the bar holds by default, for 44.6 % more bytes

Decision 19 shipped 8 colours as a stated trade: smaller than 16, and outside the 1.0 %
accuracy bar on anti-aliased marks. Two things made that the wrong trade.

**8 is not a mild miss on every mark.** On a gradient it is a broken one: in the run this
decision was taken on, 27–28 % of pixels were off by a visible margin at every size, and
favseed's own benchmark excluded the gradient from its worst-case line as "meant to be bad". A
favicon generator that wrecks a common kind of mark by default, and says so only in a
benchmark, is not making a trade users can see.

**Matched against a competitor, 8 colours is where most of favseed's byte lead came from.**
Measured 2026-10-01 against `@vite-pwa/assets-generator` 2.0.0 (sharp, `quality: 60`): fed the
same lossless pixels, favseed's encoder at 16 colours beat or matched its bytes on typical marks
(−6 % to +5 % over four files) while being more accurate on every file, and won by 30 % only
on pixel-grid marks. The large default-set gaps came from fewer files and fewer colours. Bytes
won through visible error are not a lead worth having.

256 is the quantiser's ceiling, not a target: it spends only the colours a mark needs, which is
why 64, 128 and 256 produce identical bytes on every non-gradient fixture. The 44.6 % in the
title was measured with Zopfli on, against the native pipeline (25 500 B at 8 against 36 881 B
at 256). Regenerated on the engine, Zopfli off (`docs/BENCHMARKS.md`, 9 marks, gradient
excluded, 180 + 192 + 512 px):

| `--colors` | bytes | vs 256 | worst pct |
|---|---|---|---|
| 8 | 27 850 | −27.1 % | **1.892 %** (over the bar) |
| 16 | 32 388 | −15.2 % | 0.423 % |
| 32 | 36 291 | −5.0 % | 0.114 % |
| 64 – 256 | 38 195 | 0 | **0.114 %** |

So 256 costs **37.1 % more** than 8 today, and every non-gradient raster is at least 8.8× inside
the bar. The gradient, at 29–30 % with 8 colours, scored 1.6–1.7 % at 256 while its stops were
rounded and scores 0.00–0.01 % now that they are not (decision 5).

**The default build reaches the palette through `--quality 80`.** Below 100 the quantiser
derives its palette from the quality target and `colors` is not passed at all; an explicit
`--colors` alone selects quality 100 and this ceiling, and `--colors` with a quality below 100
is an error. Over 11 fixtures, Zopfli off, quality 80 wrote 69 291 PNG/ICO bytes against 74 180
at 100 (−6.6 %), with the worst non-gradient source error 0.114 % at both
([bench/zopfli/QUALITY.md](../bench/zopfli/QUALITY.md)). With selective precision the worst
final PNG source error at the default is 0.114 % on those fixtures, gradient included
([bench/precision](../bench/precision/README.md)).

The accuracy tests score the **default** build instead of a hand-picked palette, so "inside the
bar" is a claim about what ships. `--colors 8` remains one flag away for anyone who wants the old
trade, and a test pins that it still misses the bar on `flat.svg`.

### 25. `icon.svg` keeps a `prefers-color-scheme` block

A dark-mode rule is the usual reason to ship an SVG favicon: a dark mark disappears on a dark
tab strip, and browsers apply `@media (prefers-color-scheme: dark)` inside an SVG favicon.
favseed once dropped the block without a warning. `inlineStyles` consumed
the class it selects, and csso then removed the `@media` rule as unused, the same path decision
18 closed for motion classes.

The default pass keeps every stylesheet now (decision 4), so the block survives it. The static
pass (`--no-animation`) treats a source with a `prefers-color-scheme` block the way the default
pass treats any stylesheet: `inlineStyles` is switched off when it would consume a class the
block selects, and `pruneRefs` replaces the blanket `class` removal, keeping the classes a
selector names and no others. That is the one `<style>` a static `icon.svg` can hold: the
source's rules, and the classes they select. Sources without such a block take the same path as
before, byte for byte.

The rasters do not change. resvg skips `@media` ("The @media rule is not supported. Skipped."),
so every PNG renders the light rules: a test builds `dark.svg` and the same mark with the block
deleted, and asserts the ICO, apple icon and padded icon are byte-identical. There is no dark
PNG set: no platform asks a favicon PNG for a colour scheme.

### 26. One engine: @napi-rs/image and @gfx/zopfli

favseed needed three native binaries that no npm package delivers at the versions it was
measured with (decision 15), so `npx favseed` failed on a fresh machine until the user installed
them by hand, and the website ran a separate WASM substitute. One npm package now carries the
whole raster stage, at those versions.

The spike behind it (2026-10-04):

| question | finding |
|---|---|
| One package for resvg, pngquant and oxipng? | `@napi-rs/image` (MIT, prebuilt for Linux, macOS and Windows on x64 and arm64, FreeBSD on x64, and more) bundles **resvg 0.48.1** and **oxipng 10.2.1**, the versions favseed pins. Its quantiser has been its own clean-room MIT code since 1.13.0; 1.12.x and earlier link the GPL-3 libimagequant. |
| Render fidelity | `fromSvg` never renders below 1000 px. Wrapping the icon in an outer SVG with `scale(N/vbW N/vbH) translate(-vbX -vbY)` and cropping to N×N is **pixel-identical to `resvg -w N -h N`** on 40/40 files; rendering big and resizing fails the bar (10–38 % at 32 px). The suite asserts it on 24 renders wherever resvg is on PATH. |
| Zopfli without a native build | napi's prebuilt leaves zopfli out. Re-deflating the winner's image data with `@gfx/zopfli` (WASM, Apache-2.0), keeping napi's row filters, lands within +0.21 % of oxipng's own zopfli, with identical decoded pixels on 80/80. |
| Browser | `@napi-rs/image-wasm32-wasi` gives SHA-256-identical output to the native module, in a cross-origin-isolated page. |
| Maintenance | `@napi-rs/image` has one active maintainer and past gaps of 6–14 months; `@gfx/zopfli` was last published in 2020. **Both are pinned to an exact version**; the native pipeline was kept runnable in `bench/native.mjs` long enough to take the measurement below, then retired once the comparison was recorded. |

`node bench/bench.mjs engine` (since removed) encoded the same 50 raw renders (10 fixtures at
16, 32, 180, 192 and 512 px) both ways, at 256 colours with zopfli at 120 iterations:

| pipeline | bytes | worst pct, against the raw render |
|---|---|---|
| native: pngquant (two dithers) and oxipng, the smallest of three, then `--zopfli --zi 120` | 82 605 | 0.279 % |
| engine: `pngQuantize` against `losslessCompressPng`, the smaller, then `@gfx/zopfli` | 79 614 (−3.6 %) | 0.035 % |

The total hides a split, and the split is the trade this decision takes. The gradient is
9.0 % smaller (32 586 B against 35 793 B). The nine other fixtures are 0.46 % larger together
(47 028 B against 46 812 B), from −0.2 % on `smil.svg` to +3.4 % on `wide.svg`; built as
shipped, placed at 180, 192 and 512 px, they come to 36 936 B against the native build's
36 881 B, +0.15 %. Under the priority rule a byte cost needs a reason. Here it is a few dozen
bytes on a flat mark, against no install step on any platform, one engine shared with the
website, and a gradient that is 9 % smaller.

It removes resvg, pngquant and oxipng as install steps, the PATH resolver of
decision 16, `pngquant-bin`, the `FAVSEED_RESVG`/`FAVSEED_PNGQUANT`/`FAVSEED_OXIPNG` overrides and
the `toolPath()`/`toolVersions()` exports. `engineVersions()` takes their place in the
integration cache key. The bench now measures the engine alone.

**The Zopfli now ships as `lib/zopfli.wasm`.** It compiles the exact Google Zopfli revision
`@gfx/zopfli` 1.0.15 was built from, with modern LLVM, and both hosts load it through
`lib/zopfli.mjs`. `@gfx/zopfli` stays as a development dependency only: `test/zopfli.mjs`
asserts identical compressed bytes against it at 15 and 120 iterations. Full native release
builds got 11.3–26.4 % faster on four fixtures with every byte unchanged
([bench/zopfli](../bench/zopfli/README.md)). The cache key's `zopfli` entry carries the WASM's
SHA-256, so a rebuilt binary invalidates cached sets.

The floor is `@napi-rs/image >= 1.13.0`, and the pin is exact: below 1.13.0 the package links
GPL code, and any release can change output bytes. CI builds every fixture on Linux, macOS and
Windows and fails if any file differs by a byte between them.

### 27. The engine finishes the raster jobs one at a time

Decision 13 kept the native rasters serial because oxipng spread one file across every core,
so concurrent jobs only contended. The engine's zopfli is WASM and runs on one thread, which
removes that reason, so the question was measured again before any worker pool was built.

`node bench/bench.mjs parallel`: the five `general.svg` sizes (16, 32, 180, 192 and 512 px),
encoded at 256 colours, then finished with zopfli at 120 iterations, once in turn and once with
one worker thread per file. Three interleaved repetitions on an 8-core/16-thread Ryzen 7 7840U,
median shown:

| arm | when decided | `docs/BENCHMARKS.md`, 2026-11-07 |
|---|---|---|
| in turn | 26.46 s | 19.49 s |
| one worker per file | 22.88 s (−13.5 %) | 16.33 s (−16.2 %) |

The bar for a worker pool was 20 %, and the numbers show why it cannot be reached. In the first
run the 512 px file alone took 22.88 s to finish, against 5.95 s for 180 px, 3.74 s for 192 px
and under 0.2 s for the two small sizes. A parallel build ends when its largest job ends, so the
512 px job is the floor whatever the core count, and the saving is capped at the other sizes'
share. Rejected: finishing in turn is not slower by enough to justify a worker pool, its startup
cost and the code that keeps its output order.

**What runs concurrently instead is the native work.** Jobs go through `mapImages`
(`lib/core.mjs`) in batches of up to four, within a 16 MiB working-pixel budget that counts the
renderer's 1000 px floor, and one at a time when any job is above 512 px. In Node, rendering and
both encodes are asynchronous native tasks, so they overlap; Zopfli is synchronous WASM on the
calling thread, so the finishes still run one after another. A failed batch drains before
the build rejects, and results keep their input order. Over four fixtures with Zopfli off,
bounded batches took 0.901 s against 1.151 s serial, with identical results
([bench/zopfli/DEFAULTS.md](../bench/zopfli/DEFAULTS.md)). A release build with `--zopfli`
pays for the 512 px finish; `mode: 'fast'` (15 iterations) is the answer where that wait
matters.

## History

Decisions that were superseded or reversed. Each heading is kept so that older references still
land; the text says what replaced it and where.

### 6. PNG: `pngquant --speed 1 --nofs --colors N`, then `oxipng`

Superseded by decision 26. The engine quantises with `pngQuantize` (speed 1, minimum quality 0,
the quality target as maximum) against a lossless encode (decision 7). Its measurement still
sets the order in decision 8: quantise first, because the quantiser re-encodes from scratch.
**Re-measured at 256 px over ten marks: 9 707 B in that order, 10 657 B reversed (+9.8 %)**, and
at 192 px the last native bench had 15 650 B against 18 937 B (+21.0 %). `--nofs` beat every
dither setting on bytes and still passed; `--speed 1` was smallest *and* most accurate;
`--posterize` was rejected because its least aggressive legal value (4) already missed the bar.

### 12. The SVG is emitted twice: `logo.svg` keeps the animation, `icon.svg` never has it

Replaced by one `icon.svg` that preserves animation and styling, with `--no-animation` as the
explicit static pass (decision 4). The split existed so that the favicon `<link>` never pointed
at a file carrying `<style>` and `@keyframes`. One file serves the `<link>` and a page's `<img>`
from one cacheable URL, every raster renders the same base appearance in either mode, and the
set is one file smaller: complete-set bytes fell 2.0 % across four fixtures
([bench/zopfli/DEFAULTS.md](../bench/zopfli/DEFAULTS.md)).

### 13. The rasters stay serial

Superseded by decisions 26 and 27: the native pipeline it measured is gone. It exists because an
obvious-looking parallelism win measured 12.8 s → 8.1 s in a quick hand test and **13.80 s →
14.08 s** under four interleaved repetitions. Crossing concurrency with oxipng's `--zi` later
confirmed the conclusion and refuted the stated reason: four jobs at once bought 1.4 % at
`--zi 120` (22.61 s → 22.28 s, inside the run-to-run spread) while burning 40 % more CPU, and one
file reached 8.2 of 16 cores, nowhere near the saturation first claimed. The extra cores went
into contention, not work. The engine's version of the question is decision 27.

### 15. External binaries: `resvg` and `oxipng` are documented installs; `pngquant-bin` is an `optionalDependency`

Superseded by decision 26: favseed spawns no external tools. No npm package could deliver
resvg or oxipng at the measured versions: `resvg-cli` used `--fit-width`, not `-w`, and pinned
resvg 0.34; `oxipng` on npm was 1.0.1 from 2021 (oxipng 4.0.3) and `oxipng-bin` wrapped 8.0.0,
and **neither had `--zi`**, so wiring them up would have produced larger files with no error.

### 16. Tool resolution probes; finding a path is not enough

> **Superseded by decision 26:** favseed spawns no tools, so there is nothing to resolve.

A path on disk was not proof of a working tool: `pngquant-bin` installs a Node shim that execs a
binary its postinstall downloads, and with that postinstall skipped (`--ignore-scripts`, npm's
default blocked-scripts policy) the shim is present, executable, and fails at spawn time. So
every candidate was probed with `--version` and fell through to the next tier when it did not
run, and the version strings keyed the Astro cache, since all three tools changed output bytes
across releases. `engineVersions()` holds that role now.

### 19. `--colors` stays at 8, and that is a trade rather than a clean win

> **Reversed by decision 24:** the default is now 256.

8 was ≈16 % smaller than 16 across the fixtures, and missed the 1.0 % bar on anti-aliased marks
at small sizes (`flat.svg` 1.11 %, `animated.svg` up to 1.57 % at the time) while a pixel-grid
mark scored 0.00 %. It was shipped as a trade stated in full, with a test pinning the miss.
Decision 24 records the two things that made it the wrong one: 8 wrecks a gradient, and most of
the byte lead it bought over a competitor came from visible error.

### 28. Two lanes for Zopfli: measured, not shipped

After decision 27 rejected a worker pool, a narrower design was measured: finish the largest
job, the 512 px icon, in one worker thread while the other jobs finish in turn on the main
thread. Bytes are identical by construction; the only question was wall clock, held to decision
27's 20 % bar. On `general.svg` in release mode it measured below the bar. It has the same
floor as decision 27's one-worker-per-file arm: the build still ends when the 512 px finish
ends.

The bounded-batch scheduler (decision 27) was kept instead. The default build skips Zopfli
(decision 8), so the default has no finish to put in a lane, and it is the native render and
encode work that batches overlap. For an opt-in Zopfli build, `mode: 'fast'` cuts the 512 px
wait more than any schedule can.
